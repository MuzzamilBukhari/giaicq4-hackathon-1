# Research Document: RAG Backend Service Implementation

**Feature**: 1-rag-backend-service
**Created**: 2025-12-17

## Research Findings

### 1. Qdrant Collection Schema and Search Parameters

**Decision**: Use standard Qdrant collection with text content and metadata fields

**Rationale**: Qdrant collections for RAG applications typically contain:
- `id`: Unique identifier for each document chunk
- `vector`: Embedding vector (dimension depends on model used)
- `payload`: JSON object containing:
  - `content`: The actual text content
  - `url`: Source URL of the documentation
  - `section`: Section title or heading
  - `chunk_id`: Identifier for this specific chunk

**Search Parameters**:
- `limit`: 5-10 results for context retrieval
- `score_threshold`: 0.3-0.7 depending on relevance needs
- `with_payload`: True to retrieve content
- `with_vectors`: False (not needed for retrieval)

**Alternatives Considered**:
- Alternative vector databases (Pinecone, Weaviate) - but Qdrant is already specified
- Different schema structures - standard approach is most maintainable

### 2. OpenAI-Compatible Endpoint for Google Gemini

**Decision**: Use Google's Gemini API with OpenAI-compatible endpoint pattern

**Rationale**:
- Google provides an OpenAI-compatible endpoint via their API
- Configuration requires setting `base_url` to Google's endpoint and using appropriate API key
- Example pattern: `https://generativelanguage.googleapis.com/v1beta/openai/`

**Implementation Details**:
- Set OpenAI client with custom base_url
- Use Google API key for authentication
- Ensure model names match Gemini models (e.g., "gemini-1.5-pro")

**Alternatives Considered**:
- Direct Google SDK vs OpenAI SDK with custom endpoint - chose OpenAI SDK for consistency with requirements
- Different LLM providers - Gemini is specified in requirements

### 3. Qdrant Collection Name

**Decision**: Use "book_content" as the collection name

**Rationale**:
- Descriptive and matches the use case
- Consistent with typical naming conventions
- Simple and clear for maintenance

**Alternatives Considered**:
- More specific names like "docusaurus_book_chunks" - but too verbose
- Generic names like "documents" - but less descriptive

### 4. Context Retrieval Patterns

**Decision**: Use semantic search with re-ranking approach

**Rationale**:
- Initial semantic search with Qdrant for relevant chunks
- Return top-k results (typically 5-10) based on similarity score
- Pass retrieved context to Gemini as part of the system prompt
- Include source information in responses for transparency

**Implementation Pattern**:
1. Convert user query to embedding
2. Search Qdrant collection for similar vectors
3. Retrieve top-k chunks with metadata
4. Format context for Gemini agent
5. Generate response with proper citations

### 5. Streaming Response Implementation

**Decision**: Use Server-Sent Events (SSE) with sse-starlette package

**Rationale**:
- SSE provides real-time streaming with good browser support
- FastAPI integrates well with sse-starlette
- Appropriate for chat response streaming
- Handles connection management properly

**Implementation**:
- Use `@app.stream` decorator pattern
- Stream tokens as they're generated by Gemini
- Proper error handling for connection interruptions
